## 二、Filter 三个问题的评价

### 问题 1：接口设计不匹配 — ✅ 正确

`VectorStoreAdapter.search()` 签名要求 `query: str` 为必填参数。但精确过滤场景的本质是 **metadata where 条件查询**，不需要向量相似度计算。当前 `FilterRetriever.filter_by()` 被迫编造一个 `query="故障 问题 原因 对策 车型 代码"` 来满足接口，这是设计缺陷的直接体现。

### 问题 2：代码语义不清晰 — ✅ 正确

`query="故障 问题 原因 对策 车型 代码"` 读起来像是一个语义查询，但实际只是占位符。维护者会误以为这段文本有业务含义而去调试它，这是认知负担。

### 问题 3：潜在风险 — ✅ 正确

两个具体风险点：
- **ChromaDB 行为变化**：当前 ChromaDB 的 `collection.query()` 在提供 `query_texts` 时会做 embedding + 相似度排序，即使有 `where` 过滤，返回顺序仍受 embedding 相似度影响。如果未来 ChromaDB 改变空查询或短查询的行为（比如拒绝过短输入、返回零结果），这个占位符就会出问题。
- **存储切换**：如果换到 Milvus/Qdrant/Pinecone，空字符串或无意义占位符的 embedding 行为各不相同，有的会报错，有的会返回不可预测的结果。

### 方案一评价：新增独立 filter() 接口 — ✅ 推荐

**正确性**：这是正解。语义检索和精确过滤是两种根本不同的操作，应该在接口层面分开。

**优势**：
- 接口语义清晰：`search()` 做语义检索，`filter()` 做精确过滤
- ChromaDB 原生支持 `collection.get(where=..., limit=...)`，不需要 embedding，实现更自然
- 未来切换到 Milvus/Qdrant 时，各自的 metadata filter 接口可以直接对接
- 彻底消除占位符问题

**代价**：
- `VectorStoreAdapter` 新增一个抽象方法，所有实现类需补实现
- 但当前只有一个实现（ChromaVectorStore），改动面很小

**实现建议**：
```python
# vector_store.py 新增
@abstractmethod
def filter(
    self,
    filters: dict[str, Any],
    top_k: int = 10,
) -> list[SearchResult]:
    """纯 metadata 精确过滤，不做语义检索"""
    ...

# chroma_store.py 实现
def filter(self, filters, top_k=10):
    where = {k: v for k, v in filters.items() if v is not None}
    results = self._collection.get(
        where=where,
        limit=top_k,
        include=["documents", "metadatas"],
    )
    # 包装为 SearchResult，score=1.0（无相似度计算）
    ...
```

### 方案二评价：空字符串/特殊标记 — ❌ 不推荐

**正确性**：能解决眼前的语义不清问题，但没解决根本问题。

**问题**：
- `query=""` 仍然走了 `collection.query(query_texts=[""])` 路径，依然会调 embedding
- **通义千问 text-embedding-v2 和 OpenAI embedding API 对空字符串的处理不可控**：有的返回零向量，有的直接报错 `input cannot be empty`
- 仍然把精确过滤耦合在语义检索接口上，只是换了个占位符
- 切换存储后端时，空字符串的行为更加不可预测

**结论**：方案二是治标不治本，方案一是治本。

### 我的推荐：采用方案一，并补充一点

方案一已经是最优解。补充建议：

在 `filter()` 方法的 `SearchResult` 中，`score` 字段设为 `1.0`（表示 100% 匹配过滤条件，无相似度计算）。这样在 `hybrid.py` 合并时，filter 路的分数语义也是清晰的：1.0 × filter_weight = 满分加成。而语义检索路的 score 是余弦相似度（0~1），两者量纲一致，加权 sum 后可比。

## 三、输入侧两个问题的一体化方案

### 问题分析

**问题 1（工况文件转换）**：
- 用户输入可能是工况文件（非结构化/半结构化的工况数据文件）
- 需要 LLM 调用一个外部工具（同事在做）将其转为表格或自然语言
- 我们只负责增加接口，不负责实现转换逻辑

**问题 2（自然语言可能是指令/补充）**：
- 当前流程：`parse_natural_language(text)` → `ParsedInput(description=text)` → `retrieve_from_parsed()` → 强制检索
- 问题：如果用户输入"请重点关注电池系统"或"补充信息：该车已行驶8万公里"，这些是指令/补充，不是故障描述，拿去检索会拉回不相关的工单，污染 ReAct 上下文

### 一体化方案：InputRouter（输入意图路由层）

在 `parse_input()` 和 `ReActDiagnosticAgent.diagnose()` 之间，插入一个 **InputRouter** 模块，用一次轻量 LLM 调用完成意图分类和路由。

```
用户输入
  │
  ▼
InputRouter（LLM 意图分类）
  │
  ├─ intent=diagnostic_query ──────► 提取检索 query → 预检索 → ReAct Agent
  │
  ├─ intent=instruction ──────────► 跳过检索 → 直接进 ReAct Agent 作为指令
  │
  ├─ intent=supplement ───────────► 跳过检索 → 进 ReAct Agent 作为上下文补充
  │
  └─ intent=working_condition_file ► 调用转换工具 → 转换结果再回 InputRouter
```

#### 详细设计

**1. 新增 InputIntent 枚举**（`models/input.py`）

```python
class InputIntent(str, Enum):
    DIAGNOSTIC_QUERY = "diagnostic_query"      # 故障描述，需要检索
    INSTRUCTION = "instruction"                 # 对 LLM 的指令
    SUPPLEMENT = "supplement"                   # 信息补充
    WORKING_CONDITION_FILE = "working_condition_file"  # 工况文件，需转换
```

**2. ParsedInput 扩展**

```python
class ParsedInput(BaseModel):
    # ... 现有字段 ...
    intent: InputIntent = InputIntent.DIAGNOSTIC_QUERY
    search_query: Optional[str] = None  # LLM 提取的检索用 query（仅 diagnostic_query 有值）
    # raw_input 保留原始输入，不经过任何处理
```

**3. InputRouter 模块**（新增 `agent/input_router.py`）

- 输入：原始文本 / 文件路径
- 用一次 LLM 调用（低温、短输出）完成：
  - 意图分类（4 选 1）
  - 如果是 diagnostic_query：提取适合检索的 query（去除指令性语言，保留故障描述核心）
  - 如果是 working_condition_file：标记需调用转换工具
- 输出：带 intent 和 search_query 的 ParsedInput

**5. ReActDiagnosticAgent.diagnose() 改造**

当前代码（`react_agent.py` L114-116）：


```python

    similar_cases = self._retrieve_similar_cases(parsed_input)
```

**6. ReAct prompt 改造**

- instruction 输入时：user prompt 明确告知"这是用户的操作指令，请据此调整诊断方向"
- supplement 输入时：user prompt 将补充信息作为额外上下文注入
- 这样 ReAct Agent 仍可在推理过程中主动调用 `search_similar_incidents`，只是不再被强制预检索

### 方案优劣

**优势**：
- 一次 LLM 调用同时解决意图分类 + query 提取，开销小（短输入短输出）
- 完全消除"指令被当检索词"的问题
- 工况文件转换接口独立，同事做好了接上即可
- ReAct Agent 保留在推理过程中主动检索的能力，只是不再被强制预检索
- 未来如果需要增加新的输入类型（如语音转文字、图片描述），只需在 InputIntent 里加枚举

**代价**：
- 新增一次 LLM 调用（但可以用 qwen-turbo 等轻量模型，成本极低）
- 新增一个模块和几个枚举，代码量增加约 100-150 行

**替代方案考虑**：

我曾考虑"不加 InputRouter，直接让 ReAct Agent 自己判断"的方案。但问题是：
- 当前架构在 ReAct 循环之前就做了预检索（`_retrieve_similar_cases`），这个预检索结果会进 system prompt
- 如果输入是指令，预检索结果已经污染了 prompt 上下文
- 要让 ReAct 自己判断，就必须先取消预检索，改为"ReAct 第一轮先判断意图再决定是否调用检索工具"
- 这样做改动更大，而且 ReAct 的 system prompt 会更复杂（要承担意图分类 + 诊断推理双重职责），容易导致推理质量下降

所以 **InputRouter 独立前置** 是更好的选择：职责分离，ReAct 专注诊断推理，InputRouter 专注输入理解。
