车辆故障诊断智能助手 — 答辩文档

项目名称：Diagnosis Agent v0.5.0
技术路线：LLM + 双路 RAG + 知识图谱闭环

一、解决什么问题？

传统车辆故障诊断面临三个痛点，根本上都是"经验难沉淀，回答靠幻觉"：

  1. 历史工单散落在 Excel 里，新人翻几十页才能找到相似案例，效率低
  2. 诊断报告非结构化，自然语言写出来很难自动入库统计
  3. LLM 凭空回答容易错，不知道真实历史案例是什么，说的根因和对策没有工业级证据支撑

我们的目标：让大模型基于真实历史案例推理，而不是凭记忆瞎编。

二、技术方案：LLM + 双路 RAG

2.1 标准 RAG 是什么

RAG（检索增强生成）三步走：
1. 检索：把知识库向量化，用户提问时召回相关片段
2. 增强：把召回结果塞进 LLM 上下文
3. 生成：LLM 基于真实上下文生成回答

解决"大模型不知道自己知识边界、输出幻觉"的问题。

2.2 我们为什么是双路 RAG

普通 RAG 只有一条向量检索路径，我们做了两条检索路径互补，精度更高：

用户问"MCU 报 P1A3E98 爬坡 IGBT 过温"
      ↓
┌─────────────────────────────────────┐
│  路径1：ChromaDB 向量检索            │ 语义模糊匹配现象描述
│  找"IGBT过温"等相似文本片段          │
├─────────────────────────────────────┤
│  路径2：Neo4j 知识图谱结构化召回     │ 按字段精确匹配 DTC码/车型/场景
│  找 DTC=P1A3E98 的 5 条故障记录     │
└─────────────────────────────────────┘
      ↓
  结果合并去重 → Embedding 精排 → 传给 LLM
路径 数据库 适配场景
语义检索 ChromaDB（628 条历史工单） 现象描述模糊、不知道精确 DTC 码时用
结构化召回 Neo4j 知识图谱（2036 节点/4356 关系） 有确定字段（DTC、车型、工况）时用，零误召

两条路径各自独立匹配，完全不做字段字符串拼接，最后由精排层融合排序。不会因为"车型字符串不对就召回不到结果"。

三、项目搭建思路：LangChain 架构

3.1 为什么选 LangChain

LangChain 是大模型应用开发框架，提供 Agent、Retriever、Tool 三大抽象。我们用它而非从零造轮子，核心利用三个能力：

LangChain 能力 我们怎么用
create_agent 构建 ReAct Agent，LLM 自主决定调哪个工具、查几次
BaseRetriever 统一检索器接口，Chroma 和 Neo4j 都实现这个接口，Agent 不感知差异
StructuredTool 把检索方法包装成工具，LLM 能按 schema 调用

3.2 分层架构

整个项目分六层，每层职责单一，通过标准接口串联：

┌─────────────────────────────────────────────────────┐
│  适配层 adapter/                                    │
│  FastAPI 对接上游平台（异步提交 + 回调）              │
├─────────────────────────────────────────────────────┤
│  Agent 层 agent/langchain_agent.py                  │
│  ReAct 推理循环，编排工具调用                        │
├─────────────────────────────────────────────────────┤
│  检索层 retrieval/                                   │
│  HybridRetriever 编排双路召回 + 精排                  │
│  ├─ Neo4jFaultRetriever（结构化）                    │
│  ├─ ChromaVectorRetriever（语义）                   │
│  └─ SemanticReranker（Embedding 精排）              │
├─────────────────────────────────────────────────────┤
│  知识层 knowledge/                                   │
│  对话抽取实体关系 → 审核 → 写回图谱                   │
├─────────────────────────────────────────────────────┤
│  上下文层 agent/context/                             │
│  三层记忆 + 话题检测 + 异步摘要                       │
├─────────────────────────────────────────────────────┤
│  存储层 storage/ + Neo4j + ChromaDB + Redis           │
└─────────────────────────────────────────────────────┘

3.3 Agent 工具集

Agent 通过 LangChain StructuredTool 暴露 4 个工具，动态注册（Neo4j 不可用时不注册 query_fault_graph，自动降级）：

工具 触发场景 数据源
search_similar_incidents 模糊匹配故障现象 ChromaDB 向量检索
query_fault_graph 有 DTC/车型等结构化字段 Neo4j Cypher 查询
get_incident_detail 查看工单详情 历史记录
convert_working_condition_file 解析工况文件 文件转换

四、实际工作流

4.1 端到端流程

一次诊断从用户提问到输出，完整经历以下步骤：

1. 用户输入
   "MCU报P1A3E98爬坡IGBT过温，车辆抖动"
        ↓
2. 输入解析 + 意图分类
   提取 entities: {dtc:P1A3E98, project:H37A, ...}
   判定意图: diagnostic_query（电驱诊断）
        ↓
3. 预检索（双路 RAG 召回）
   ├─ ChromaDB: 找到 5 条"IGBT过温"相似工单
   └─ Neo4j: 找到 DTC=P1A3E98 的 3 条图谱记录
   合并 → Embedding 精排 → 取 top_k
        ↓
4. ReAct Agent 推理循环
   Thought: 需要查这个 DTC 的根因
   Action: query_fault_graph(dtcCode=["P1A3E98"])
   Observation: 根因=IGBT散热基板焊接不良
   Thought: 证据够了，下结论
   Final: 输出结构化诊断 JSON
        ↓
5. 双层输出
   ├─ 人类可读：Markdown 诊断报告
   └─ 机器可读：CSV/JSON（含分类、根因、对策、相似工单ID）
        ↓
6. 知识沉淀
   LLM 抽取本轮对话的 实体/关系 → 写入待审核队列
        ↓
   完成

4.2 CAN 报文兜底

当预检索结果不足（top1 相似度 < 0.6）时，自动触发 CAN 报文解码，把信号数据补充进 Agent 上下文：

预检索相似度低 → 解码 CAN 工况文件 → 信号摘要注入 → Agent 基于信号推理

支持 ASC/BLF/MF4/CSV 等多种 CAN 日志格式，结合 DBC 文件解码为物理值。

4.3 三层记忆系统

多轮对话的上下文管理，三层存储 + 三步降级，解决长对话 Token 预算问题：

层级 内容 存储 触发降级条件
热层 完整消息 Redis 超 window_size → 摘要后移温层
温层 滚动摘要 Redis 摘要超上限 → 合并精简
冷层 归档 JSON 磁盘 话题切换/会话结束 → 归档

Redis 不可用时自动降级内存，跨会话可从冷层恢复。

五、核心创新点

创新点 普通 RAG 我们的方案
检索模式 单路向量 双路混合 RAG（Chroma 语义 + Neo4j 结构化）
LLM 角色 上下文生成器 ReAct 推理编排者（主动调用工具查资料）
知识库 静态 动态闭环（自动抽取 → 审核 → 写入图谱）
多轮记忆 无/简单 三层分层记忆（热/温/冷），支持话题切换和跨会话恢复
兜底机制 无 CAN 报文自动解码，检索不足时注入信号上下文
输出格式 纯文本 双层输出（人读 Markdown + 机读 CSV/JSON）

六、效果展示

6.1 一次完整诊断的输出

用户输入"MCU报P1A3E98爬坡IGBT过温"，系统输出：

人类可读报告（Markdown）：
- 故障分类：过温故障
- 根因分析：IGBT 散热基板焊接不良，动态行驶中螺丝耸动与 PCB 电容接触短路
- 解决方案：优化作业流程，将螺纹孔深度纳入作业流程管理
- 相似工单：5 条（含车型、工况、软件版本）
- 仪表指示灯：电机故障红灯

机器可读条目（JSON）：

{
  "classification": "过温故障",
  "root_cause": "IGBT散热基板焊接不良",
  "solution": "优化作业流程",
  "dtc_code": "P1A3E98",
  "similar_record_ids": ["REC-1ff8...", "REC-0ece..."],
  "confidence": 0.91
}

故障分类强制从 10 类固定列表选择（驱动异常/控制异常/超速/高压异常/低压异常/过温/通信/旋变/状态机/油泵），保证分类一致性。

6.2 数据规模与测试

指标 数值
测试用例 87 个（全部通过，41 秒）
向量库记录 628 条历史工单（1024 维 text-embedding-v4）
知识图谱 2036 节点 / 4356 关系（8 类实体 / 13 类关系）
检索策略 hybrid（Neo4j + Chroma 双路）
LLM 后端 通义千问 deepseek-v3.1
Token 预算 8000，热层窗口自适应 2~20 轮

6.3 性能指标

  • LLM 推理响应：单轮 0.4~1.0 秒（e2e 实测）
  • 检索召回：top1 相似度 0.71~0.93 区间符合预期
  • 温层摘要压缩：合并后总 Token 减少 60%
