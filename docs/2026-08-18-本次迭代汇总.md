## 三、预检索优化

### 实现

- 话题检测通过后，Agent 调用前，先做一轮 Chroma 语义检索（~500ms）
- 结果直接注入 system prompt，Agent 可直接分析，无需每轮都调工具
- Prompt 策略：预检索充分时直接推理，不足时允许 Agent 自行编辑检索词补充检索

### 性能数据

- 预检索命中时，Agent 减少大量工具调用
- 诊断耗时从 50-70s →30-55s

## 四、Bug 修复清单

### 4.1 流式打印问题彻底解决

- **根本原因**：两套回调冲突，旧回调硬编码 120 字符截断
- **改动**：
  - 删除 `cli.py` 中遗留的 `_stream_print` 函数
  - 启用 Agent 自带的 `_enable_react_stream()` 新回调
  - 工具调用 / 工具返回 / Agent 推理三部分分别用黄/绿/蓝色标题高亮，JSON 使用 monokai 主题 Syntax 格式化展示
- **效果**：不再出现符号，不再截断内容，ReAct 步骤全量可见

### 4.2 Chroma 距离阈值方向 Bug 修复

- **根本原因**：ChromaDB `similarity_search_with_score` 返回的是 cosine distance（距离，越小越相似），三处过滤逻辑全写反 `>=`
- **原始错误现象**：完全匹配（距离 0.23/0.27）的记录被阈值 0.3 过滤丢弃，只有距离 0.38 的低相关记录通过
- **改动**：将所有三处 `if result.score >= threshold` 改为 `<=`

### 4.3 阈值逻辑全局统一重构

- **问题**：三处独立维护的重复代码（`_get_relevant_documents` / `search_with_filters` / 预检索），极易出现方向写反的低级错误
- **改动**：
  - 在 `ChromaVectorRetriever` 中提取公共私有方法 `_filter_and_wrap_results(results)`
  - 全局仅此一处阈值判断入口，统一 SearchResult → Document 转换
  - 预检索层删除多余二次过滤逻辑，直接复用 `semantic_search()` 返回已过滤好的结果
- **收益**：消灭所有重复逻辑，后续不可能再出现方向写反问题

### 4.4 `query_fault_graph` 参数兼容 + Neo4j 自动移除

- `tools.py`：`QueryFaultGraphInput` 新增 `@field_validator('dtc_code', mode='before')`，兼容 LLM 传 JSON 字符串或逗号分隔字符串
- `tools.py`：`DiagnosticTools.__init__` 中加 Neo4j 连通性检查（`RETURN 1`），不可达时 `get_tool_list()` 不注册 `query_fault_graph`

### 4.5 Rich Syntax 主题修复

- **问题**：JSON 高亮用 `theme="default"` 在暗色终端背景下显示全白，可读性差
- **改动**：两处 Syntax 调用 theme 改为 "monokai"，暗色终端下代码高亮效果正常

## 六、知识沉淀模块完成 + Web 审核页面

### 6.1 GraphDocument 基础设施接入

**背景**：之前用手写原始 Cypher MERGE 写入 Neo4j，不符合 LangChain 生态标准，后续其他诊断项目接入时需要重复开发。

**实现**：
- 从 `langchain_neo4j.graphs.graph_document` 导入 `GraphDocument` / `Node` / `Relationship`（项目已预装 `langchain-neo4j`，无需额外依赖）
- `Node.type` 统一设为 `"__Entity__"`，实体类型存入 `properties.entity_type`
- 调用 `add_graph_documents(graph_docs, baseEntityLabel=False, include_source=False)` 走 APOC 的 `apoc.merge.node` 路径，兼容 Neo4j 5.x
- 实体去重逻辑通过 `Neo4jGraph.query()` 实现三模式匹配：`e.id == name OR e.name == name OR e.description CONTAINS name`

**效果**：6 实体 + 4 关系端到端写入验证通过，GraphDocument 基础设施完全对齐 LangChain 标准，后续其他诊断项目直接复用。

### 6.2 分隔符配置化（多项目模板化预留）

**背景**：不同诊断项目（混动/电池/充电）可以自定义元组分隔符，避免 LLM 输出格式冲突

**改动**：
- `config.yaml` knowledge 段新增 3 字段：
  - `tuple_delimiter: ":"` — 实体和关系字段之间的分隔符
  - `record_delimiter: ")"` — 记录结束标记
  - `completion_delimiter: "返回空列表"` — 无内容时的输出提示
- `prompts.py` 动态注入占位符，LLM 输出格式随配置自动生成
- `extractor.py` 正则基于分隔符动态编译（`re.escape()` 自动转义特殊字符）

### 6.3 提取模型配置化

- 新增 `knowledge.extraction_model: "deepseek-v3.1"` 配置
- 从硬编码改为读配置，`qwen3.5-plus` 实测结构化提取返回空不适合知识提取，默认使用 `deepseek-v3.1`
- 测试记录存入 `memory/reference_knowledge_extraction_model.md`

### 6.5 Chat 模式自动提取 Bug 修复

- **根本原因**：`langchain_core.messages.messages_to_dict()` 返回格式为 `{"type": "human", "data": {...}}`，但 `_auto_extract_knowledge()` 原来过滤条件只认 `m.get("role") in ("user", "assistant")`，永远匹配不到，导致消息列表为空，知识提取静默跳过。
- **修复**：两处兼容：
  1. `cli.py` 过滤条件改为 `m.get("type") in ("human", "ai") or m.get("role") in ("user", "assistant")`
  2. `extractor.py` `format_conversation()` 兼容 `data.content` 嵌套结构
- **效果**：chat 模式自动提取后，控制台正常打印 `知识已提交审核: xxx...`

### 6.6 相似工况展示 Bug 修复

- **根本原因**：预检索 `semantic_search()` 直接返回 5 条相似工况注入 System Prompt，但 `_extract_similar_cases_from_tools()` 只从 Agent 工具调用结果中提取，预检索结果全部漏掉，最终显示 0 条
- **修复**：在组装 `similar_case_models` 时，先把预检索的 Document 转为 SimilarCase 模型，再用工具调用结果补充去重
- **效果**：相似工况数目与日志里"预检索: 找到 X 条相似工况"保持一致
